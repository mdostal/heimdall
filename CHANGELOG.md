# Changelog

## [Unreleased]

### Added

- **`hdl-claude-subscription-lanes` epic complete.** `provider: "claude"` lanes now support two credential shapes, auto-detected — a raw Anthropic API key (unchanged) and a Claude Code long-lived OAuth token (`sk-ant-oat01-...`, from `claude setup-token`), closing a real gap between the north star's "2-5 Claude Code subscriptions" framing and the API-key-only adapter shipped since `lane-health-status`. Confirmed via research that Anthropic's Messages API rejects this token type directly outside the genuine Claude Code client, so the correct integration path shells out to the real `claude` CLI, reusing the `CommandRunner` pattern already established for Multica (`CommandRunner.run()` gains an additive, backward-compatible env-override option). **A live adversarial test caught a real design flaw before it shipped**: the originally-planned `claude auth status --json` check reported a fabricated token as valid even in a fully isolated environment — it only inspects a token's shape, never validates it against Anthropic's servers. Replaced with a real minimal completion call (`claude -p ... --max-turns 1`), verified correct in both directions against a fabricated token and a genuine one — the one active-probe in the codebase that spends real, non-zero inference, since there's no free way to validate this credential type. See `.pHive/epics/hdl-claude-subscription-lanes/docs/research-brief.md`. Version bump `0.15.0` → `0.16.0`.

- **`hdl-mcp-routing-strategy` epic complete.** Closes the follow-up explicitly deferred when `hdl-routing-strategies` shipped: two new MCP tools, `heimdall.routingStrategy.get` (returns `{ active, available }`, identical shape to `GET /routing-strategy`) and `heimdall.routingStrategy.set` (`{ strategy }`, wraps the existing `setRoutingStrategy` shared function — invalid names return structured `{ error: "invalid_strategy", allowed_strategies }` content rather than throwing). Zero new business logic — both tools call the exact same shared functions the HTTP routes already use. Version bump `0.14.0` → `0.15.0`.

- **`hdl-ollama-signals` epic complete — closes the north star's provider list to 6/6.** Ollama gets a liveness-only signal adapter, per operator decision ("liveliness it doesn't really have a path -- it should have liveliness so we can signal off of it mostly") — only `up`/`down`, no `degraded`/`out_of_credit`/`reset_at`, since none of those have a real signal for local unauthenticated inference. `active-probe/ollama.ts` hits `GET <baseUrl>/api/tags` with no auth. Implementation research found a cleaner path than originally anticipated: rather than making `Lane.credential` optional (touching `lane-registry.ts`/`route-selector.ts`/`lane-pipeline.ts`'s credential-gating logic), the existing `credential_ref` indirection is repurposed to carry the Ollama instance's base URL instead of a secret (e.g. `HEIMDALL_LANE_<N>_CREDENTIAL_REF=OLLAMA_HOST`, `OLLAMA_HOST=http://localhost:11434`) — this flows through the completely unmodified pipeline, and as a side benefit supports multiple Ollama instances on different hosts (north_star's "scales... as hardware/instances are added") with zero new declaration fields. Wired via the usual `ollamaAdapters()` + `PROVIDER_ADAPTERS` entry. See `.pHive/epics/hdl-ollama-signals/docs/design-discussion.md`. Version bump `0.13.0` → `0.14.0`.

- **`hdl-openrouter-signals` epic complete.** OpenRouter now nests as a gateway with independently toggleable, judged routes underneath it, per operator decision — not one more flat lane. A dedicated codebase research pass confirmed the persistence layers needed zero schema changes (`lane_id` is the only identity key anywhere; multiple lanes already shared one `credential_ref` today). Closed the two real gaps found: `active-probe/openrouter.ts` (`GET /api/v1/key` — a single call returning both credit balance and rate-limit state, richer than a bare list-models probe; no `public-status/openrouter.ts` since no confirmed machine-readable feed exists) wired via the usual `openrouterAdapters()` + `PROVIDER_ADAPTERS` entry, proven end-to-end with two lanes sharing one credential and independently recording status/override; the dashboard now shows each lane's `model` and groups lanes sharing a gateway `credential_ref` under one header (`GET /lanes` gains `model`/`credential_ref`, both non-secret metadata already on the in-memory `Lane`); and an optional `HEIMDALL_LANE_<N>_PRIORITY` override lets the operator rank same-provider routes directly (`priority-strategy.ts`'s table-driven rank was previously blind to same-provider ties) — unset is byte-identical to prior behavior, mirroring `manual_override`'s override-wins-outright shape. See `.pHive/epics/hdl-openrouter-signals/docs/design-discussion.md`. Version bump `0.12.0` → `0.13.0`.

- **`hdl-kimi-signals` epic complete.** Kimi K3 (Moonshot AI) is now a fourth supported lane provider — 4 of 6 north-star providers now have signal adapters. `active-probe/kimi.ts` mirrors `codex.ts`'s Bearer-auth + OpenAI-API-compatible-host pattern (`GET api.moonshot.ai/v1/models`), reading a typed `error.type` vocabulary that distinguishes transient conditions (`engine_overloaded`, `too_many_requests` → `degraded`) from longer-lived quota exhaustion (`billing_quota_exhausted`, `monthly_quota_exhausted`, `rolling_quota_exceeded` → `out_of_credit`) — richer than Codex's own undocumented guesswork. `public-status/kimi.ts` is a near-verbatim mirror of `claude.ts`: `status.moonshot.cn` is a real Atlassian-Statuspage feed (confirmed via its `api/v2/summary.json` endpoint), a better fit than Gemini's incidents.json workaround. Wiring was the same 3-line addition established by the last two provider epics (`kimiAdapters()` + one `PROVIDER_ADAPTERS` entry). See `.pHive/epics/hdl-kimi-signals/docs/design-discussion.md`. Version bump `0.11.0` → `0.12.0`.

- **`hdl-gemini-signals` epic complete.** Gemini is now a third supported lane provider — closes the largest concrete gap against the north star's provider-scale target (`Claude, Codex, Gemini, OpenRouter, Kimi K3, Ollama`; only 2 of 6 had signal adapters before this epic). Real web research into Gemini's actual signal surface informed two new adapters mirroring the existing `claude.ts`/`codex.ts` pattern exactly: `active-probe/gemini.ts` (`GET generativelanguage.googleapis.com/v1beta/models`, authenticated via the `x-goog-api-key` header rather than the leakier `?key=` query param; a 429 body's `error.status`/`message` distinguishes a transient rate limit — `degraded` — from a longer-lived daily quota condition — `out_of_credit`) and `public-status/gemini.ts` (Google Cloud's `status.cloud.google.com/incidents.json` feed, fragment-filtered to Gemini/Vertex-AI-related products since — unlike Claude's fixed per-component snapshot — this is a flat, Google-Cloud-wide incident list with no positive "operational" entry to read). One confirmed, documented gap versus Claude: the Gemini Developer API has no reset-timestamp field for 429s, so `reset_at` is always `null` for Gemini probes — `InProcessScheduler`'s existing reset_at-unknown fallback (`hdl-reason-aware-recovery`) already handles this gracefully. Wiring was a 3-line addition to already-provider-agnostic code (`geminiAdapters()` in `lane-pipeline.ts`, one `PROVIDER_ADAPTERS` entry in `main.ts`) — `Lane`/`LaneDeclaration`, `LanePipeline`, route selection, and every HTTP/MCP/UI surface needed zero changes, confirming the `ProviderSignalAdapter` pattern actually generalizes. See `.pHive/epics/hdl-gemini-signals/docs/design-discussion.md`. Version bump `0.10.0` → `0.11.0`.

- **`lane-health-status` epic complete (v1/P0).** Health/status detection for Claude and Codex lanes across a layered signal model (passive observation, public status-page piggybacking, sparse active probes), a corroboration policy guarding against provider false-positives, and the `LaneRouterContract` — a synchronous request/response query surface exposed identically over HTTP (`GET /lanes`), CLI (`npm run cli`), and MCP (`heimdall.lanes.list`). SLA-verified: status correctness within 10 seconds of an actual state change (measured, not asserted — see `test/sla-harness/report.md`). `/execute` applied the planned `minor` version bump (`0.1.0` → `0.2.0`) to keep the package version in lockstep with this release.
- **`hdl-scheduler` epic complete.** Pluggable per-lane `Scheduler` interface with two HARD-LAW-compliant backends — `MulticaAutopilotScheduler` (default, coarse cron via the real Multica CLI, ≥1min floor) and `InProcessScheduler` (fine ~5s, suspect-lane only, backs off immediately on recovery). Every tick and status flip emits OTEL to Argus (the first Node/TypeScript OTLP client in Pantheon). Added `POST /lanes/:laneId/refresh` (the trigger endpoint Multica's dispatched agent calls) and a stubbed third interaction mode (`ActuationStub`, future Multica runtime on/off toggling). `src/main.ts` is now the real service entrypoint. See `docs/decisions/DEC-hdl-scheduler-backend.md`. `/execute` applied the planned `minor` version bump (`0.2.0` → `0.3.0`).
- **`hdl-actuation` epic complete (v2).** Heimdall now actually actuates, not just senses: `MulticaControlAdapter` calls Multica's real REST API to disable/re-enable a lane's mapped agents (`max_concurrent_tasks: 0`/`N` — the verified-safe lever, corrected from the original design doc's wrong `status`/`archive` proposal) via a flaky-connection-hardened `MulticaRestClient` (timeout + never-throws `MulticaCallResult`) wrapped in a generic `CircuitBreaker`. Lane → agent mapping is explicit config (`HEIMDALL_LANE_<N>_MULTICA_AGENT_IDS`) behind a `LaneAgentResolver` interface. Every lane always gets a `ControlAdapter` — mapped lanes get the real `MulticaControlAdapter`, everything else (including the whole service when Multica isn't configured at all) falls back to a loud `StubControlAdapter`, never a silent no-op. `reconcile()` runs every sense-loop tick for every lane, giving idempotent retry-for-free on partial failures, with every attempt emitted to Argus (`emitActuationResult`). Tested entirely against local mocks — the real hive Multica instance (`:8090`) is never called by this test suite; live end-to-end verification is an explicit operator follow-up. See `docs/decisions/DEC-hdl-role-actuation.md`. `/execute` applied the planned `minor` version bump (`0.3.0` → `0.4.0`).
- **`hdl-reason-aware-recovery` epic complete.** Lane recovery now consumes the `reason`/`reset_at` data Heimdall already captures, instead of treating status as the only signal. `InProcessScheduler` schedules a suspect lane's next probe at its known `reset_at` (e.g. an out-of-credit reset timestamp) instead of blindly polling every 5s, floored at the existing interval so a past/stale `reset_at` can never busy-loop; falls back to the existing flat interval when `reset_at` is unknown. `ControlAdapter.reconcile` now optionally carries `reason`/`reset_at` alongside status, so `MulticaControlAdapter`'s Argus emission (`lane.reason`/`lane.reset_at` span attributes) and `StubControlAdapter`'s recorded actions can say *why* a lane is blocked, not just that it is — out-of-credit-until-reset_at and down-for-unknown-reason are now distinguishable in telemetry. The block/allow actuation decision itself is unchanged. See `docs/decisions/DEC-hdl-reason-aware-recovery.md`. Version bump `0.4.0` → `0.5.0`.
- **`hdl-lane-status-ui` epic complete (slice 1).** First vertical slice of Heimdall's standalone-mode UI requirement (`has_ui: true`): `GET /` now serves a self-contained, dependency-free read-only dashboard (inline HTML/CSS/JS, no build step, no framework) that polls the existing `GET /lanes` endpoint every 5s and renders lane status with a color-coded badge, reason, and a human-formatted `reset_at`. Pure consumer of already-shipped data — no new backend query logic. Manual disable/enable, add-lane, and the MCP agent-tooling surface for the same operations are explicitly deferred to follow-up epics. See `.pHive/epics/hdl-lane-status-ui/docs/design-discussion.md`. Version bump `0.5.0` → `0.6.0`.
- **`hdl-lane-override` epic complete.** Manual lane disable/enable, routed through the *existing* `ControlAdapter.reconcile()` decision rather than a separate mechanism — a per-lane `manual_override` (`enabled`/`disabled`/`null`) wins outright over the sensed status when set (byte-identical behavior when unset), exposed via `POST /lanes/:laneId/override` (`state: enabled|disabled|auto`) and surfaced on `GET /lanes`. `MulticaControlAdapter`'s Argus emission gains `overrideActive` so an override-driven block/allow is distinguishable from a status-driven one in telemetry. The dashboard (`hdl-lane-status-ui`) gets per-lane Enable/Disable/Auto controls plus a "manual: …" badge that's always visible when an override is active — never silent. See `docs/decisions/DEC-hdl-reason-aware-recovery.md` item 3 and `.pHive/epics/hdl-lane-override/docs/design-discussion.md`. Version bump `0.6.0` → `0.7.0`.
- **`hdl-lane-management` epic complete.** Closes out the remaining UI scope of `has_ui: true`: (1) `.env` is now auto-loaded (`--env-file-if-exists=.env`, zero new dependency) — fixes a standing gap where the operator had to manually source it; (2) `POST /lanes` adds a new lane, writing a `HEIMDALL_LANE_<N>_*` block to the local, gitignored `.env` (Portunus remains the deferred fix for real secret storage) and naming the exact restart command, no automatic restart; (3) `GET /lanes` gains `credential_configured: boolean` — visibility into token status without ever serializing the raw secret; (4) manual `reset_at` ("change the times") mirrors `manual_override`'s pattern exactly — an operator-set recovery time wins over the sensed one in `InProcessScheduler`'s already-shipped reset_at-aware delay computation, scheduling-only. The dashboard gets an Add Lane form, a token-configured chip, and an editable reset-at control with its own "manual" badge. See `docs/decisions/DEC-hdl-reason-aware-recovery.md` item 3 and `.pHive/epics/hdl-lane-management/docs/design-discussion.md`. Version bump `0.7.0` → `0.8.0`.
- **`hdl-mcp-lane-tools` epic complete — closes `DEC-hdl-reason-aware-recovery.md` item 3 in full.** `override`/`reset-at`/`add-lane`'s HTTP-route validation logic is extracted into shared functions (`setLaneOverride`/`setLaneResetAt`/`addLane` in `src/api/http-server.ts`), mirroring `getLaneStatuses`'s existing shared-across-surfaces role — a behavior-preserving refactor verified by the full pre-existing HTTP test suite passing with zero test changes. Three new MCP tools (`heimdall.lanes.override`, `heimdall.lanes.setResetAt`, `heimdall.lanes.add`) wrap those functions alongside the original `heimdall.lanes.list`, so an agent can exercise/test every lane operation Heimdall supports, not just query status. Validation failures return structured content rather than throwing — only a genuinely unrecognized tool name produces a real MCP protocol error. See `.pHive/epics/hdl-mcp-lane-tools/docs/design-discussion.md`. Version bump `0.8.0` → `0.9.0`.
- **`hdl-routing-strategies` epic complete.** Resolves the north_star's own `avoid` clause ("don't hard-code routing heuristics ... must be A/B-testable/reconfigurable"): route selection is now pluggable behind a `RoutingStrategy` interface (`src/core/routing-strategies/`) — `priority` (today's original ranking, still the default), `round-robin` (cycles through eligible lanes), and `off` (never picks — the caller decides via `GET /lanes` instead). Selected via a new global settings table on `StateStore` and `GET`/`POST /routing-strategy`. Also fixes a real gap found along the way: `manual_override` didn't previously affect `/available-route` at all — a disabled lane could still be recommended. It now gates candidacy with the exact same override-wins-outright precedence `MulticaControlAdapter` already uses, so "block the usage and direct it around" actually works end-to-end. Dashboard gets a simple settings panel to pick the active strategy, with the `off` state's consequence always visibly flagged. See `.pHive/epics/hdl-routing-strategies/docs/design-discussion.md`. Version bump `0.9.0` → `0.10.0`.
